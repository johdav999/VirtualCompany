# Continuous agent dialogue — implementation prompts

Created 2026-09-28. Execute prompts 1–7 in order. This document describes implementation work; creating it does not execute the prompts.

## Target experience

After the organizer presses **Start agent** and participant consent is satisfied, Alex joins as a continuously available voice participant. A greeting can receive a spoken reply immediately. A spoken presentation request starts the approved prerecorded deck. Alex continues listening while narration plays. She uses the conversation and available tools to decide whether to clarify, respond socially, explain a general concept, retrieve approved company sources, pause narration, or start/resume it. After an answer she can ask a relevant follow-up, wait, answer another question, or resume when clearly requested.

Dialogue wording and interpretation are generated by the model. Backend permissions, content-release rules, playback ownership and state transitions remain explicit. Presentation playback is a capability of the conversation, not a replacement for it.

### Authority and release policy

- Autonomous: permitted conversational speech, eligible grounded answers including qualified partial answers, and authorized presentation commands can execute without a per-answer approval click.
- Assisted/manual: preserve existing approval, exact answer version and **Speak approved answer** behavior. Preserve existing mode-specific presentation controls. New automatic dialogue/actions are autonomous-only in this pack; do not expand lower-mode permissions implicitly.
- Realtime selects a proposed action. The backend validates access, actor/controller rights where needed, consent, mode, ownership, current generations, content-release policy, idempotency and limits at execution and publication.
- Social conversation and clearly general educational explanations can use a separate permitted release class. Company capabilities, pricing, onboarding commitments, customer records and other restricted claims require approved evidence. Model classification cannot grant itself a less restrictive release class.
- Never publish unrestricted model audio and rely only on instructions or a later transcript to enforce grounding. Validate restricted speech before any of its audio reaches participants. Preserve the approved-answer release path.
- Silence, fan noise, an unclear acknowledgement or a stale proposal is not authorization to start/resume a deck. Stop AI, takeover, consent withdrawal, room end and usage limits retain precedence.
- Keep agent presence, input listening, output speech and presentation playback separate. A normal turn completion or recoverable rejected turn must not dispose the media session. A stopped session must not pretend to remain connected.
- Preserve usage, consent and audit history. Do not reschedule meetings, reset counters, raise limits, auto-consent, unmute devices or alter external calendar events to make acceptance pass.

## Prompt 1 — Keep a started agent present and listening independently of playback

### 1. Title and outcome

Implement a reusable persistent conversation lifetime so **Start agent** establishes an available meeting participant throughout presentation, pauses, answers and idle listening.

### 2. Current context

Use the shared implementation map. Existing lease and media lifetime are already managed by the room worker. Reply availability is additionally constrained by previous answer/bridge state and time windows; those restrictions must no longer define whether an authorized started agent can receive a fresh turn.

### 3. Dependencies

None beyond the current checkout and existing room/provider configuration. Deterministic tests need no live credential.

### 4. Implementation requirements

- Integrate independent conversation availability, input listening, presentation checkpoint and output-owner state into the existing controller/worker. Do not create a competing floor or lease owner.
- Feed fresh authorized turns into the provider context from initial join, between slides, while paused, after answers, and after a former reply window expires. Retain bounded historical context, while distinguishing stale action proposals from fresh input.
- Remove the mandatory preceding answer and 45-second gate for accepting a new conversation turn. Keep short expiry and generation checks for individual proposed actions.
- Continue renewing ownership during idle listening, retrieval and playback. Recoverable turn rejection preserves the connection; terminal events stop it and fence pending work.
- Keep the existing approved answer/playback route working at this stage. New unrestricted conversation speech is delivered in prompt 3.
- Use existing persistence where sufficient. If durable state is necessary, identify the fields and provide EF migrations and SQL Server checks under the canonical database rules.

### 5. Constraints and preservation rules

Apply all shared instructions. Preserve recently fixed stale-turn isolation, accumulated usage and real stop behavior. Do not automatically replay old speech when reconnecting.

### 6. Acceptance criteria

- Given a started, authorized agent, when narration finishes or pauses, then its media participant and listening session remain available.
- Given no previous answer, or more than 45 seconds since one, when a fresh permitted utterance arrives, then it enters conversation processing.
- Given an obsolete response failure, then it cannot pause/cancel the current turn; given consent withdrawal or meeting end, then AI listening/output stop.

### 7. Verification

Exercise relational worker lifetime, leases, idle input, current/stale generation, replacement owner, tenant isolation, consent and limits. Build affected backend projects. Record actual media connection receipts separately from inferred status.

### 8. Definition of done

The lifetime is implemented in the running worker with regression coverage and updated policy documentation. Availability is truthful and the existing authorized question flow still works.

## Prompt 2 — Deliver complete spoken turns through the Realtime conversation profile

### 1. Title and outcome

Implement semantic Realtime turn handling so pauses within a question are preserved and the persistent agent receives the actual audio needed for live interpretation.

### 2. Current context

The shared PCM conversation profile currently disables provider turn detection and relies on local segmentation/manual commits. Local completeness buffering already exists. Choose one authoritative commit/completion path for the new profile rather than layering two independent turn creators.

### 3. Dependencies

Prompt 1. Existing authorized microphone transport and a compatible configured Realtime model. Provider credentials are required only for live verification.

### 4. Implementation requirements

- Add an explicit opt-in shared conversation profile with semantic VAD and configurable eagerness, initially testing `low`. Keep existing profiles unchanged. Use current documented event/configuration fields.
- Send authorized PCM with participant/track provenance, bounded pre-roll and continuity sufficient for sentence completion. Local detection may reduce unnecessary forwarding, but must not cut off beginnings/endings or commit at each short silence before semantic detection can work.
- Use provider turn completion to assemble/correlate utterances. Prevent duplicate manual/provider commits and duplicate transcription, routing or response creation. Retain local safeguards for noise, echo, overlapping speakers and incomplete input.
- Keep response creation and external narration interruption under application control. Provider speech-start alone must not grant a presentation action or publish an unchecked answer.
- Route incomplete/uncertain input to waiting or model-generated clarification rather than guessing a company topic. Preserve transcript-retention permissions; identify the supported path when retention is declined instead of silently storing text.
- Add bounded timeout/recovery and observability for capture start, final turn, routing and response. Transient turn failures must not destroy an otherwise healthy session.

### 5. Constraints and preservation rules

Apply shared instructions. Semantic VAD is a completion aid, not an authorization check. Keep raw microphone audio ephemeral and account for all forwarded input.

### 6. Acceptance criteria

- Given “A question, how…” followed by a pause and “…do you onboard companies?”, then one complete question reaches routing.
- Given fan noise or presentation echo, then no answer/presentation command is authorized solely by volume.
- Given a duplicate or out-of-order provider event, then the turn executes once; changed speaker/track/consent boundaries never merge.

### 7. Verification

Run provider-schema/event replay, segmentation/completeness, tenant/participant provenance, retention and timeout tests. Measure the real RØDE USB mic flow, pause sensitivity and fan/echo cases using an authorized audience; explicitly record unavailable live access.

### 8. Definition of done

The new profile handles real input end to end and has compatible fallback/recovery. It does not claim semantic VAD is active while still overriding it with the old manual-commit path.

## Prompt 3 — Let Realtime route dialogue and deliver permitted conversational speech

### 1. Title and outcome

Deliver an immediate spoken greeting and ongoing natural dialogue, with Realtime choosing a proposed response/action and the backend enforcing its release class.

### 2. Current context

Current acknowledgements require an earlier released answer, and a separate classifier pins the Realtime tool. Reuse shared context and validated speech infrastructure while replacing those gates for the new profile.

### 3. Dependencies

Prompts 1–2. Existing approved-speech and grounding integrations. Compatible provider credentials for live audio checks.

### 4. Implementation requirements

- Let the Realtime model select among currently permitted social response, general explanation, clarification/wait and approved-source lookup proposals. Use automatic selection, not a classifier-selected `RequiredToolName` or keyword/phrase table. Safety validators may reject proposals but must not substitute a generic company answer.
- Define structured proposals tied to the latest trusted input turn. Model arguments cannot choose company, identity, permissions, mode or playback checkpoint. Dispatch only complete correlated function calls; return their real result and correlate any continuation once.
- Support greetings, thanks, clarification and follow-up immediately after join and at any later authorized listening point. No prior question/evidence row is required for these lanes.
- Provide model instructions for role, concise style, conversation context, uncertainty and tool use. Generate dialogue wording; do not hardcode greeting/follow-up scripts.
- Implement a real conversational-audio lane using the shared Realtime adapter. Hold output until the backend validates the permitted content class and current authority. Correlate candidate text/audio, validate the completed output, and only then publish through the room media path. A text-only tool session plus unchanged old bridge path is not completion of this prompt.
- For company-specific/restricted content, route to the existing grounded release and approved speech path. General content must remain explicitly general and cannot contain unverified company/customer commitments. Add independent release checks; a model-chosen label alone is insufficient.
- If output is withheld, continue listening and expose an actionable reason. Record buffering latency and any approved-speech fallback; do not pretend a fallback is direct streamed Realtime audio.

### 5. Constraints and preservation rules

Apply shared instructions. No unchecked output may escape before validation. Keep conversation context bounded and include only legitimately heard input and actually delivered responses.

### 6. Acceptance criteria

- Given initial join with no earlier answer, when a participant welcomes Alex, then she gives a brief generated spoken response.
- Given “thank you” after an answer or a long pause, then she can acknowledge without a source lookup or automatic resume.
- Given unclear input, then she clarifies rather than describing the company generally. A restricted claim mislabeled as general is withheld/routed to grounding.

### 7. Verification

Test model proposal dispatch with recorded provider fixtures, wrong/duplicate/stale call IDs, unauthorized and cross-company proposals, restricted-content misclassification, output leakage and continued listening after rejection. Run a real provider greeting exchange and report the output path and latency honestly.

### 8. Definition of done

An authorized participant can hold a spoken social exchange from join. Model-selected routing is integrated; generated audio has a working enforced release boundary and no scripted dialogue substitute.

## Prompt 4 — Expose presentation playback as authorized dialogue tools

### 1. Title and outcome

Allow spoken start, pause and resume requests while Alex stays in the conversation, with a single controller preventing overlapping narration and conversational audio.

### 2. Current context

Reuse the conductor, approved narration, durable speech queue, floor publisher, saved offsets and current continuation service. Existing continuation depends on a recently played answer/bridge; fresh explicit commands must work independently of that history.

### 3. Dependencies

Prompts 1–3. An approved playable deck and audience readiness. No new external calendar integration is needed.

### 4. Implementation requirements

- Implement model-selectable start presentation, pause presentation, resume saved presentation and read presentation state tools. Distinguish start/restart from continuation. Reuse current host command semantics and backend authority.
- Advertise only actions currently available to that participant/mode. For non-controller participants, allow a question where already permitted, but require current controller authority for presentation commands.
- Add an output arbiter shared by approved narration, grounded speech and conversational audio. Its generation/token ownership must prevent simultaneous output and stale cancellation/completion mutating newer speech.
- On an accepted interruption, cancel/flush old narration, save the actually played offset, and let dialogue own output. Listening remains active throughout. A brief greeting/backchannel during narration need not always interrupt; let the model propose an action and enforce it.
- Resume from the durable narration checkpoint, not answer-audio duration or an invented model position. Keep context updated with current slide, playback state and completed/partially played narration based on real receipts. For interrupted Realtime audio, truncate using actual delivered position through the provider adapter.
- Deduplicate commands and recheck consent, mode, versions, audience, approved asset and limits at execution/publication. Return acceptance versus actual playback completion accurately.
- A generated offer to continue never starts playback until a clear fresh request/reply is authorized. Ambiguous assent to a multi-part offer must be clarified.

### 5. Constraints and preservation rules

Apply shared instructions and the canonical Workflow/Approval and External Side Effects/Outbox rules for playback commands. Preserve manual controls, full-deck continuation, stale-turn isolation and checkpoint fixes. No schema change is expected; justify and migrate any necessary persistence addition.

### 6. Acceptance criteria

- Given listening after join, when the organizer asks to present, then approved prerecorded narration starts and microphone input remains available.
- Given accepted question interruption, then narration stops at a measured checkpoint; a later resume continues there once.
- Given an old narration failure after a new answer is queued, then the answer remains authorized and can play. Silence, duplicates and unauthorized commands do not start a deck.

### 7. Verification

Use relational tool/worker tests and media receipts for output exclusivity, actual offsets, retries, mode changes, controller rights, tenant isolation, question preemption and deck advancement. Re-run the real greeting → start → interrupt → resume flow.

### 8. Definition of done

The tools execute real existing playback commands and are available to Realtime. Presentation and conversation coexist with one authoritative output owner and truthful context.

## Prompt 5 — Keep factual answers grounded, concise and conversational

### 1. Title and outcome

Answer the participant's actual question briefly, retrieve when facts require evidence, and return naturally to dialogue without unnecessary approval in autonomous mode.

### 2. Current context

Existing question answering supports approved company knowledge, document evidence, partial answers and exact-version release. Preserve that implementation while integrating it with continuous dialogue and separating general education from company facts.

### 3. Dependencies

Prompts 1–4. Existing authorized, indexed sources and AI provider configuration. Do not grant new document access automatically.

### 4. Implementation requirements

- Carry the complete confirmed utterance and relevant bounded conversation context into retrieval. Preserve provenance and follow-up references without replacing the user's question with a guessed product topic.
- Enforce source requirements for capabilities, pricing, onboarding commitments and customer data. Allow a clearly general explanation only under the separate permitted content policy; do not call a company-specific onboarding answer “general” to bypass grounding.
- Compose sales answers around 2–3 short sentences and roughly 40–60 words by default. Preserve supported claims, important qualifications and one concise missing-detail statement. Put citations and fuller evidence in the private panel rather than reading source identifiers aloud.
- Automatically release eligible complete/partial answers in autonomous mode. Preserve explicit host review/speech in assisted/manual. Recheck answer version, content and authority before publication.
- After speech actually completes, return to persistent listening. Generate a relevant optional follow-up using what was asked and heard; accept new questions or clear continuation without a mandatory bridge or 45-second gate.
- Distinguish insufficient evidence, rejected input, provider failure and authorization changes. A recoverable retrieval or speech-validation failure must not dispose a healthy meeting session or replay an old answer.

### 5. Constraints and preservation rules

Apply shared instructions. Preserve exact approved speech, limitations, citation scope and existing document access. No calendar/database test resets or automatic source permission expansion.

### 6. Acceptance criteria

- Given “How is onboarding done?” with partial approved evidence, then Alex speaks the supported steps and a brief qualification automatically in autonomous mode.
- The same answer in assisted/manual requires the existing approval/speech action.
- Given missing evidence or malformed input, then no fabricated company overview or historical answer is played. A fresh valid question can still be processed afterward.

### 7. Verification

Test grounding, partial release, question fidelity, length/claim preservation, changed source/answer version, tenant/agent access, speech matching, mode downgrade and recovery. Verify an indexed document question with actual evidence and playback receipts.

### 8. Definition of done

The complete question-to-spoken-answer path is integrated with dialogue, concise and source-enforced. Follow-up and resume operate from actual delivered context.
