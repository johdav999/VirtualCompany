# Marketing operations runbook

Provider permissions, supported actions, OAuth requirements, limitations, and official documentation links are maintained in [marketing-channel-provider-contracts.md](marketing-channel-provider-contracts.md). Executable release evidence and unresolved repository-wide test baselines are recorded in [marketing-release-verification.md](marketing-release-verification.md).

OAuth is disabled by default. For each enabled provider, configure its client ID, protected client-secret reference where required, access tier, and an exact HTTPS `AllowedRedirectUris` allowlist under `Marketing:ChannelOAuth`. Register that identical callback with the provider. An empty allowlist intentionally blocks authorization. Do not enable the delivery worker until destination discovery, approval policy, secret-store writes, and reconciliation have been exercised in the target environment.

This runbook covers Maya's governed Marketing strategy, segmentation, content, channels, measurement, events, and independent operating loop.

## Safe operating model

- Company goals, operating initiatives, pause state, budgets, and effective authority remain authoritative.
- Maya may analyze and prepare internal artifacts within her effective authority. External publication requires an exact, current approval and a connected provider capability.
- A channel action is durable and idempotent. It moves through `proposed`, `awaiting_approval`, `queued`, `dispatching`, and a terminal or recoverable state.
- Unknown provider outcomes are `ambiguous`. Do not manually replay them until the provider state has been reconciled.
- Company members can read Marketing state. Company managers perform Marketing mutations and request governed runs.

## Provider configuration

Set `Marketing:ChannelDelivery:Enabled` only after the protected secret store and provider applications are configured. Defaults are intentionally safe:

```json
{
  "Marketing": {
    "ChannelDelivery": {
      "Enabled": false,
      "PollSeconds": 30,
      "BatchSize": 20,
      "MaximumAttempts": 5,
      "LinkedInVersion": "202604",
      "MetaGraphVersion": "v24.0"
    },
    "CreativeImage": {
      "Enabled": false,
      "Model": "gpt-image-2",
      "ApiKeySecretReference": "platform/openai/api-key"
    },
    "AssetSafety": {
      "Enabled": false,
      "Provider": "unavailable",
      "Endpoint": "",
      "ApiKeySecretReference": "",
      "ScannerVersion": "unconfigured-v1",
      "TimeoutSeconds": 60
    },
    "JourneyWorker": {
      "Enabled": false,
      "PollSeconds": 30,
      "BatchSize": 25
    }
  }
}
```

Provider credentials are resolved through `IPlatformSecretStore`; Marketing tables contain only a reference. The reference must begin with `companies/{companyId:N}/marketing/`. Never put access or refresh tokens in API payload fields, capabilities JSON, logs, or Marketing records.

Connections currently support approved text publishing through LinkedIn Posts and X Posts, Facebook Page feed publishing, and single-image Instagram publishing from an approved public image URL. Provider application review, scopes, manageable destination discovery, OAuth callbacks, and real-account verification remain environment-specific prerequisites. A connection's `capabilitiesJson` must explicitly list allowed action names.

Governed creative generation uses the configured OpenAI image model only when `CreativeImage:Enabled` is true. The default model is `gpt-image-2`; its API key is loaded from the protected platform secret reference and must never be placed in application settings. Generated bytes are written through `ICompanyDocumentStorage` under a company-scoped Marketing key.

Every generated or uploaded file is sent to the deployment-owned HTTPS scanner configured under `Marketing:AssetSafety`. Its API key is resolved from `IPlatformSecretStore`. The bounded scanner response persists provider, immutable provider reference, scanner version, time, result, reason, checksum-linked evidence, malware/content-safety/privacy/prohibited-content findings, and a safe details reference. `pending`, `failed`, `error`, missing, disabled, invalid, or unreachable scanner states quarantine the asset and block submission, approval, download, and publication. File storage, MIME/signature checks, and an image provider's generation safety string are not treated as authoritative malware scanning. Configure the scanner, correct its health/credential, and create a new scan before release.

A company manager can request that new scan through `POST /api/marketing/creative-assets/{assetId}/rescan` or the Marketing workspace. Rescanning reads the company-scoped stored object through a 25 MB bounded stream, verifies its immutable checksum, persists every scanner attempt, and writes an audit event. It never replaces prior scan evidence or changes the asset bytes.

Relational tables store only company-scoped storage keys, checksums, scanner evidence, provider references, and immutable asset family/version metadata. Operators can request changes on a submitted version; an approved version is never overwritten.

The journey worker must remain disabled until consent evidence, suppression data, channel connections, approvals, and delivery reconciliation are operational. It rechecks current consent and suppression before every action. Withdrawing consent or adding suppression exits the enrollment without dispatch. Every journey action still requires its own approval; the worker does not treat journey activation as blanket publishing authority.

Maya strategy and content generation use the shared reasoning gateway. Strategy proposals are previews until a manager explicitly creates an idempotent draft. Content generation persists only source-grounded output and records its reasoning run, capability/prompt versions, source references, and immutable variant family/version.

Strategy decomposition reuses the existing Sales campaign aggregate. It previews a dependency tree first, then commits an idempotent Marketing plan, campaign activities, content briefs, durable work tasks, and a strategy/segment/campaign trace link. It never launches the campaign. Content edits create a new immutable variant-family version; approved history is retained. Creative metadata can be changed only while the asset is a draft, regeneration always creates a new family version, and only an approved asset can be retired.

The deterministic Marketing policy service is authoritative for strategy/campaign/audience activation, outbound communication, publication, spend, tracking, regulated claims, brand review, target selection, segment changes, and destructive actions. Use `POST /api/marketing/governance/preview` to inspect the stable reason code, plain-English explanation, approval role, and evidence for an immutable target version. Approval never overrides missing evidence, consent, suppression, tenant isolation, or prohibited sensitive targeting.

Observation corrections are append-only. Submit a new observation with `correctionOfObservationId`; the prior value remains available as lineage but is marked superseded and excluded from experiment, Maya-analysis, and company-snapshot calculations.

## Operator recovery

| State | Meaning | Safe action |
|---|---|---|
| `awaiting_approval` | A manager decision is pending | Decide in Approvals, then use Check approval |
| `retry_scheduled` | A retryable provider or rate-limit failure occurred | Let the worker retry within the attempt limit |
| `reauthorization_required` | The protected credential was rejected or missing | Renew the provider credential; do not replay first |
| `ambiguous` | The request may have reached the provider | Check provider state/reference before any retry |
| `failed` | A permanent policy, validation, capability, or provider error occurred | Correct the source artifact and prepare a new immutable action |
| Creative `quarantined` / scan `pending` | No authoritative passing scan is available | Configure or restore the scanner, rescan, then submit the immutable asset version |
| Creative scan `failed` | Malware or content-safety policy rejected the file | Keep it unavailable; investigate the safe scanner evidence and upload a corrected file |
| Creative scan `error` | The authoritative scanner failed or returned an invalid contract | Check scanner health/credential and retry scanning; do not download or publish |
| Marketing run `blocked` | Company pause, missing evidence, invalid assignment, budget, or capability stopped Maya | Resolve the displayed recovery code, then request a new governed run |
| Marketing event `failed` | Event analysis or its dependency could not complete | Open the linked durable task, correct the evidence/provider condition, then process again |
| Marketing event `processed` | Maya reviewed the event and linked evidence/work | Resolve it only after the operator-visible response is complete |

## Database and deployment

Apply the EF migrations through the normal deployment pipeline. The Marketing migrations are additive in `Up` and use SQL Server-compatible types and indexes, preserving both local SQL Server and Docker restore/run flows. Before deployment:

Development startup (`server.ps1`) uses `appsettings.Development.json` and applies pending EF migrations before hosted schedulers and workers start. Other environments remain conservative: when startup migration application is disabled, the API fails before workers start and lists the pending migration IDs. Apply them explicitly from the repository root with:

```powershell
dotnet ef database update --project src/VirtualCompany.Persistence.Migrations/VirtualCompany.Persistence.Migrations.csproj --startup-project src/VirtualCompany.Api/VirtualCompany.Api.csproj --context VirtualCompanyDbContext
```

The same command is authoritative for local SQL Server and the Docker SQL Server connection selected through configuration. Do not use `EnsureCreated`, manually create `company_operating_configurations`, rewrite `__EFMigrationsHistory`, or reset a database to repair drift. `/health/ready` distinguishes an unreachable database, pending migrations, a missing schema object, migration-validation failure, and a ready migrated database through its `database` result and `readinessCode`.

If a worker reports SQL Server error 208 for `company_operating_configurations`, stop the affected host, inspect `__EFMigrationsHistory`, run the command above against the intended connection string, confirm migration `20260812072032_AddCompanyOrchestrationAndMarketingFoundation` is present, and restart one API host. Escalate rather than deleting data if the migration fails. A `TokenExpired` mailbox connection is a separate reconnect condition and does not justify database repair.

1. Back up the database using the environment's normal SQL Server process.
2. Run the EF pending-model check and inspect the generated SQL in the target release pipeline.
3. Apply migrations to a restored copy or staging database before production.
4. Confirm tenant query filters and company-scoped unique indexes.
5. Enable the Marketing delivery worker only after secrets and provider app approvals are ready.
6. Enable creative generation and lifecycle journeys independently only after their protected secret, storage, consent, and approval checks pass in staging.
7. Verify the asset scanner over HTTPS with a harmless test file and an approved malware test fixture; confirm the former passes, the latter remains quarantined, and no raw file or credential appears in logs.

## Verification checklist

- API and Web projects build.
- Focused Marketing, approval-boundary, segmentation, orchestration, and provider validation tests pass.
- Duplicate idempotency keys return the existing record.
- A rejected, expired, cancelled, mismatched, or missing approval never queues or dispatches an action.
- Revoked credentials produce operator-visible reauthorization without secret leakage.
- Ambiguous HTTP outcomes are not blindly retried.
- Maya's operating snapshot reports missing segments, observations, connections, or attribution evidence.
- Replayed Marketing events for the same type/source/version/day return one event and at most one linked response task.
- Corrected observations retain both records while only the current value contributes to analysis and experiments.
- Policy preview denies suppressed or non-consented outbound work even when approval is marked complete.
- Desktop and narrow Marketing views retain readable status, evidence, and safe actions.
- Missing/disabled/error scanner behavior is fail-closed, and only a persisted authoritative `passed` result enables asset use.

## Live provider blockers

Live LinkedIn, Meta, and X checks require a reviewed provider application, the documented scopes, an approved company-owned destination, an enabled paid/access tier where applicable, protected credentials, and explicit cost authorization. When any prerequisite is absent, keep the provider disabled or show `unavailable` / `reauthorization_required`; fixture tests and compilation are not recorded as live-provider success.

## External verification record

Record each real provider test separately with company, provider application/environment, destination type, granted scopes, action type, provider reference, normalized result, reconciliation result, and timestamp. Never copy credentials or raw personal/provider payloads into the record.
